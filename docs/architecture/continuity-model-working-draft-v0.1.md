# Continuity Model Working Draft v0.1

## Status

Founder-approved working model for documentation consolidation. This is an architecture-oriented product model, not an implementation plan and not a schema specification.

## Core model

Continuity is the maintained relationship among:

1. prior supported state;
2. new evidence or events;
3. meaningful change;
4. current significance;
5. present attention;
6. evidence lineage;
7. human verification and correction.

## State categories

- **Current truth**: the present operational projection used for current work.
- **Historical truth**: what was true, generated, observed, or understood at an earlier time.
- **Maintained conclusion**: a supported conclusion preserved across time until reconciled, corrected, resolved, or replaced.
- **Evidence lineage**: the source trail that supports a maintained conclusion and allows verification.
- **Attention state**: what requires awareness or action now.

## Reconciliation

Reconciliation determines whether a maintained conclusion remains current, needs monitoring, is resolved, or should be replaced by a newer supported conclusion. Reconciliation must not rewrite historical truth and must not become an autonomous reasoning authority.

## Candidate shared concerns

The following concerns may belong in a Shared Continuity Foundation after validation across applications:

- state identity;
- temporal comparison;
- maintained conclusions;
- meaningful-change representation;
- evidence lineage;
- present relevance;
- reconciliation;
- current-versus-historical authority;
- attention state;
- correction consequences.

## Application-specific concerns

Clinical significance, progression, reassessment, treatment implications, clinical safety, and clinician verification are Clinical Continuity concerns unless explicitly validated elsewhere. Care state, responsibilities, observations, instructions, communication, and caregiver attention are future Care Continuity concerns and are not implemented here.

## Implementation boundary

This model may guide classification and audit work. It does not authorize technical extraction, schema changes, API changes, persistence changes, ranking changes, AI behavior changes, or application-code changes.
